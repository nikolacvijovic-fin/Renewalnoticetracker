# Future Activation Rules

A deferred capability may only become active runtime behavior when all of the following are true:

1. It is listed in the canonical deferred capability registry with an updated activation decision.
2. The shipped kernel still passes boundary tests without hidden imports or navigation leakage.
3. A runtime owner can explain why the capability improves first value, weekly operator habit, trust, paid conversion, or support reduction.
4. The capability has explicit authz, trust, billing, and release-test coverage before activation.
5. Customer-facing docs, pricing, settings, and tests are updated in the same change.

Activation is not allowed based on “we might need this later.” Preserved code is not permission to surface it.
